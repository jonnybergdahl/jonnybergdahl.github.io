Detailed Description

Home Assistant MQTT device discovery publisher (transport-agnostic).

Typical usage:

  • Construct with a MqttTransport implementation
  • Provide device info via setDevice(), before connecting (this sets the Last Will)
  • Register a command handler with onCommand() if you have switches or buttons
  • Connect through the transport
  • Add entities with the publish*Discovery() methods
  • Call tick() from loop(), and publish states as needed

The publish*Discovery() methods add or update an entity. The device payload with all entities is published from the next tick(), so adding several entities in setup() sends one message. States published before that are sent right after it.

Everything is kept in RAM so it can be sent again after a reconnect or a Home Assistant restart: about 150–250 bytes per entity. The device payload (about 400 bytes plus that per entity) is built from it only while it's being published.

◆ migrateEntityDiscovery()

void HaDiscovery::migrateEntityDiscovery ( bool enable = true)

Take over the entities this node has on single-component discovery topics.

Older firmware often publishes one discovery message per entity, on <discovery_prefix>/<component>/<node_id>/<object_id>/config. If those are still retained on the broker, Home Assistant keeps those entities, and ignores entities in the device payload that have the same unique_id.

With this turned on, the library subscribes to <discovery_prefix>/+/<node_id>/+/config and follows Home Assistant's migration steps for every config it finds there: it publishes {"migrate_discovery": true}, then the device payload, and clears the old topic a few seconds later. Home Assistant keeps the entities and their settings.

Only configs whose unique_id matches an entity in the device payload are migrated (see HaEntityCommon::unique_id), so add the entities before connecting. Others are left alone and logged as a warning; Home Assistant then shows the old entity next to the new one, instead of losing it.

Up to 64 of these retained configs are handled per tick(), apart from the normal limit of 16 incoming messages.

After every connect, the device payload waits until those retained messages are in. To know when, the library also subscribes to <base>/<node_id>/migration_sync and publishes a message there; the broker sends it back after the retained configs. That usually takes well under a second, with a limit of 10 seconds. Once the old topics are cleared nothing more happens, so it's fine to leave it on.

Call it before connecting.

Parameters
enableWhether to migrate (default true)

◆ onCommand()

void HaDiscovery::onCommand ( HaCommandCallback cb)

Set the handler for commands from Home Assistant.

It's called when a message arrives on the command topic of an entity that takes commands: switch, button, number, select, text, light or cover. After acting on it, publish the new state (publishStateSwitch(), publishStateNumber(), publishStateLight(), publishState() or publishStatePosition()).

Commands are queued when they arrive and the handler is called from tick(), so it always runs in loop(), also with AsyncMqttClient.

Parameters
cbCommand handler

◆ onMessage()

void HaDiscovery::onMessage ( HaMessageCallback cb)

Set a handler that gets incoming messages as they arrived, with their topic.

It's called for commands to entities (before the onCommand() handler, with the payload as it arrived) and for messages on topics added with subscribe(). It's not called for the messages the library handles itself: the Home Assistant birth message and migrateEntityDiscovery().

Use it when your firmware already has its own MQTT command handling, or for topics that don't belong to an entity. Like onCommand(), it's called from tick().

Parameters
cbMessage handler

Publish a light state as JSON, e.g. {"state":"ON","brightness":128,"color_mode":"brightness"}.

The color_mode is set from what's included: color, then color temperature, then brightness, otherwise onoff.

For a light with HaLightSchema::Default, each part goes to its own topic instead: "ON"/"OFF", the brightness, "r,g,b" and the color temperature, the ones the light has.

◆ republishAll()

void HaDiscovery::republishAll ( )

Publish the device payload, availability "online" and the last states now.

This happens automatically on every connect, after entity changes and after a Home Assistant birth message. Does nothing while disconnected.

If the transport doesn't accept the device payload or availability (for example when the MQTT client is short of memory), tick() tries again after a delay that grows from PUBLISH_RETRY_MIN_MS to PUBLISH_RETRY_MAX_MS. States are held until then.

◆ tick()

void HaDiscovery::tick ( )

Periodic processing hook. Call this from loop().

It drives the transport (connection changes and reconnect), handles queued commands and birth messages, and does all publishing:

  • after a connect: subscribes, then publishes the device payload, "online" and the stored states
  • after entities were added or removed: publishes the device payload and the stored states
  • after a Home Assistant birth message and a random delay: publishes everything again
